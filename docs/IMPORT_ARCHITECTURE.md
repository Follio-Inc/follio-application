# Follio Import Architecture Documentation

## Overview

This document describes the canonical data model, import service interfaces, and merge rules used by Follio to handle data from multiple sources (resume uploads, GitHub, LinkedIn, etc.).

## Canonical Data Model

Follio uses a **canonical data model** where all imported content is normalized into a consistent schema. The UI reads from this canonical schema, not from raw import sources.

### Key Principles

1. **Imports are inputs, not truth** - Imported data is transformed and stored in the canonical model
2. **Provenance tracking** - Each field tracks its source (`MANUAL`, `GITHUB`, `RESUME`, `LINKEDIN`, `GENERATED`)
3. **User edits win** - Manual edits always take precedence over imported data
4. **Deduplication** - The system automatically deduplicates entries across sources

### Profile Schema (Prisma)

```prisma
model Profile {
  id     String        @id @default(cuid())
  userId String        @unique
  handle String        @unique // URL slug: /u/[handle]
  status ProfileStatus @default(DRAFT) // DRAFT | PUBLIC | PRIVATE

  // Basic info with provenance
  firstName       String?
  firstNameSource DataSource @default(MANUAL)
  lastName        String?
  lastNameSource  DataSource @default(MANUAL)
  headline        String?
  headlineSource  DataSource @default(MANUAL)
  summary         String?
  summarySource   DataSource @default(MANUAL)
  location        String?
  locationSource  DataSource @default(MANUAL)
  avatarUrl       String?
  avatarUrlSource DataSource @default(MANUAL)

  // Auto-generation tracking
  isAutoGenerated        Boolean   @default(false)
  autoGeneratedAt        DateTime?
  autoGeneratedDismissed Boolean   @default(false)

  // Relations
  contactInfo     ContactInfo?
  links           Link[]
  workExperiences WorkExperience[]
  educations      Education[]
  skills          Skill[]
  projects        Project[]
  dataSources     DataSourceConnection[]
}
```

### DataSource Enum

```prisma
enum DataSource {
  MANUAL // User entered manually
  GITHUB // Imported from GitHub
  RESUME // Extracted from resume upload
  LINKEDIN // Imported from LinkedIn
  GENERATED // AI-generated suggestion
}
```

## Merge Rules

### Priority Order

```typescript
const SOURCE_PRIORITY: Record<DataSource, number> = {
  MANUAL: 100, // User edits always win
  RESUME: 80,
  LINKEDIN: 70,
  GITHUB: 60,
  GENERATED: 50,
};
```

### Protected Fields

These fields are never auto-overwritten:

- `handle`
- `userId`
- `id`
- `createdAt`

### Merge Strategies

1. **Scalar fields** (firstName, headline, etc.)
   - First non-empty value wins during initial import
   - Manual edits always override imports
   - Higher priority source wins when both have values

2. **Array fields** (skills, experiences, projects)
   - Append new items from imports
   - Deduplicate based on key fields:
     - Skills: by `name`
     - Experiences: by `company` + `title`
     - Projects: by `repoUrl` or `title`
     - Links: by `url`
   - Never delete user-added items

### Deduplication Keys

| Entity           | Deduplication Keys        |
| ---------------- | ------------------------- |
| Skills           | `name` (case-insensitive) |
| Work Experiences | `company` + `title`       |
| Education        | `institution` + `degree`  |
| Projects         | `repoUrl` OR `title`      |
| Links            | `url` (case-insensitive)  |

## Async Processing

For long-running operations (e.g., resume parsing), the system uses an `ImportJob` model:

```prisma
model ImportJob {
  id          String     @id @default(cuid())
  userId      String
  source      DataSource
  status      JobStatus // PENDING | PROCESSING | COMPLETED | FAILED
  progress    Int        @default(0) // 0-100
  currentStep String? // Human-readable status
  result      Json? // Normalized data on success
  error       String? // Error message on failure
  startedAt   DateTime?
  completedAt DateTime?
}
```

### Job Polling

```typescript
// Check job status
const response = await fetch(`/api/import/jobs/${jobId}`);
const job = await response.json();

if (job.status === 'completed') {
  // job.result contains normalized data
}
```

## Extending the System

### Adding a New Import Source

1. Create a new service file in `services/import/`:

```typescript
// services/import/newSource.service.ts
import type { INewSourceImportService, ImportServiceResult } from './types';

export class NewSourceImportService implements INewSourceImportService {
  async importNewSource(credentials: unknown, userId: string): Promise<ImportServiceResult> {
    // 1. Validate input
    // 2. Create ImportJob for tracking
    // 3. Fetch data from source
    // 4. Normalize to NormalizedImportResult
    // 5. Store raw payload for debugging
    // 6. Update DataSourceConnection
    // 7. Return normalized result
  }
}
```

2. Add the interface to `types.ts`

3. Export from `index.ts`

4. Create API route in `app/api/import/newSource/route.ts`

5. Add UI in onboarding import hub

### Improving Resume Parsing

The current resume parser (`services/resume-parser.service.ts`) uses basic heuristics. To upgrade:

1. The interface is defined in `services/import/types.ts`
2. Implement a new parser that returns `ParsedResume`
3. Swap the implementation in `resume.service.ts`

No changes needed to:

- Onboarding UI
- Merge logic
- API routes

## Error Handling

All import services follow this pattern:

```typescript
interface ImportServiceResult {
  success: boolean;
  data?: NormalizedImportResult;
  error?: string;
  errorCode?: string; // VALIDATION_ERROR, NOT_FOUND, IMPORT_ERROR
  jobId?: string;
  status?: 'completed' | 'processing' | 'failed';
}
```

The UI displays friendly errors and allows users to continue even when imports fail.

## Security Considerations

1. **File validation**
   - Max size: 5MB
   - Allowed types: PDF, TXT, DOC, DOCX

2. **Text sanitization**
   - Remove null bytes and control characters
   - Limit stored raw text to 50KB

3. **OAuth tokens**
   - Stored encrypted in `DataSourceConnection.accessToken`
   - Never exposed to client

4. **Rate limiting**
   - GitHub API has rate limits; handle gracefully
   - Resume parsing should be rate-limited per user
