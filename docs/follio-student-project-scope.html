What Follio is

Follio is a professional first impression. A person captures their data once — by uploading a resume, connecting GitHub, or editing directly — and Follio turns that into one shareable link.

Follio The card people share: name, contact, call, email, save to contacts.
Resume Printable, ATS-friendly document from the same data.
Work Selected work, when the owner chooses to show it.

The product is a live web application (Next.js, TypeScript, PostgreSQL). Students will contribute to that codebase. This is not a throwaway class project.

Why this project exists

Follio needs two things that sit beside the core product:

  1. A stronger Developer Platform so the team can monitor and test the app as it changes.
  2. A public Follio API so third-party software can read a user’s data, with permission.

A mobile MVP for Google Play and the App Store is optional. Take it on only after the Developer Platform and API are in good shape. Carissa and Padmaja will own the required workstreams. Follio will provide product direction and code review, and store accounts if mobile is started.

01

Workstream

Developer Platform

Goal. Make it easy and reliable for Follio developers to see if the app is healthy, and to test real user journeys without guessing.

What already exists

Follio already has an internal Developer Platform at /admin/developer (admin-only). It is a working first version, not yet a polished daily tool. It includes:

  • Health checks (database, required environment, feature flags)
  • Vitest suite runner (local only)
  • Live QA — Playwright journeys such as landing page, sign-in, resume upload, builder, and share / visibility
  • Resume reader lab (parse a PDF without saving it to a profile)
  • Manual smoke checklist and quick links into the app

What students will do

  • Make the platform something a Follio engineer would open every day
  • Improve Live QA: more stable pathways, clearer pass / fail, better failure reports
  • Add coverage for journeys that break most often (onboarding, share, public Follio, resume)
  • Make health and smoke views obvious when something is wrong
  • Document how to add a new test pathway
  • Optional stretch: start a Users monitoring view for operators (a placeholder already exists)

In scope

  • Developer Platform UI and backend
  • New Live QA pathways and fixtures
  • Local-only test runners (never in production)
  • Clear loading, empty, error, and success states

Out of scope

  • Replacing CI (GitHub Actions already runs lint, types, tests, and build)
  • Changing product UX just to make tests easier
  • Remote-control of production browsers or user machines

Done when

  • A Follio engineer can open the Developer Platform and know, in under a minute, whether the local app is healthy
  • Critical user journeys can be run from the UI and from the command line
  • Failures explain what broke in product language, not only a stack trace
  • Adding a new pathway is documented and follows a predictable set of steps
02

Workstream

Follio API (read)

Goal. Let a third-party app read a user’s Follio data, with explicit permission, through a stable HTTP API.

Example consumers: a job-application tool, a personal CRM, a campus career portal, or an extension that is not Follio’s own.

What already exists — and is not the same thing

Existing piece Why it is not the public API
Internal profile APIs Session auth for the Follio web app only
Export endpoints (JSON, text, PDF) File download of a resume, not a partner integration
AI connector / MCP Built for AI assistants; includes draft / write. Different audience
Chrome extension APIs Cookie auth for Follio’s own extension

Students will design a partner-facing, read-only API, reusing profile data and visibility rules. Write access is not part of this term.

What students will do

  • Define a versioned REST API (for example /api/v1/...)
  • Authenticate third-party clients (API keys and/or OAuth). A user must grant access; a random app cannot scrape private data
  • Respect Follio visibility: public, unlisted, private, and share tokens
  • Return a clean JSON model of what the third party is allowed to see: identity, contact (if shared), experience, education, skills, projects, links
  • Publish developer documentation: auth, endpoints, example requests, error codes, rate limits
  • Ship a small demo client that reads a Follio with a token
  • Add tests for auth, visibility, and the happy path

In scope

  • Read-only access to profile data the owner has chosen to share
  • Auth, rate limiting, versioning, error format
  • Docs a third-party engineer can follow without a walkthrough

Out of scope

  • Write, update, or delete of profile data
  • Billing or a public developer marketplace
  • Replacing the existing AI connector / MCP

Done when

  • A third-party app can obtain permission, call the API, and receive JSON that matches the user’s shared Follio
  • Private data is never returned without permission
  • Docs and a demo client exist
  • Automated tests cover auth failure, missing profile, private profile, and successful read
03

Optional workstream

Mobile MVP Optional

Optional. If the Developer Platform and API are solid and time remains, help ship a first Follio app that a real person can install and use for the core “open and share my Follio” loop. This is stretch work. It is not required to complete the project.

If this workstream is started, students help build the MVP. Follio owns Apple and Google developer accounts, signing, and store listing copy. Students own implementation and store-readiness of the app itself.

Follio is web-only today. There is no iOS or Android app yet.

What a user can do in the MVP

Signed-in owner

  • Sign in
  • See their Follio
  • Copy / share their Follio link
  • Open Resume and Work when those are enabled
  • Basic account actions (sign out at minimum)

Visitor who opens a shared Follio

  • See the Follio card
  • Call, email, or save to contacts
  • Open Resume / Work when the owner made those public

In the mobile MVP

  • Auth, view, share, and connect
  • Cross-platform app talking to the same Follio backend
  • Empty, error, and signed-out states
  • Store assets: icon, screenshots, short description

Not in the mobile MVP

  • Full resume builder / designer
  • AI resume parse and onboarding upload
  • Cover letter builder
  • Admin or Developer Platform
  • Offline-first editing

Those stay on the web. Mobile is the share-and-connect surface first. React Native / Expo is the likely stack, confirmed if this workstream starts. Do not rewrite the web product.

Done when (only if this workstream is taken on)

  • A TestFlight build and an internal Play Store testing track exist
  • The flows above work on one iOS device and one Android device
  • Auth, empty profile, network error, and signed-out states are handled
  • Store listing assets are prepared
  • Follio can submit. Apple / Google approval is not required for the academic “done” line, but the binary must be submittable

How work is split

Two people, two required workstreams. Mobile is optional later, not a third required track.

Person Primary (required) If time remains
Student A Developer Platform Help the API, then optional mobile
Student B Follio API Help the Developer Platform, then optional mobile

Both students should be able to run the web app, explain the data model, and review each other’s pull requests. If one required workstream finishes early, that student helps the other first. Mobile is a joint stretch only after both required pieces are demoable.

Working agreement

Students will:

  • Work in the existing Follio repository, on feature branches, via pull requests
  • Follow Follio’s engineering bar: TypeScript, tests for new logic, no secrets in git, no production-only hacks
  • Keep CI green: lint, typecheck, format, and tests
  • Join a weekly check-in with Follio (demo + blockers, 30 minutes)
  • Not ship directly to production

Follio will provide:

  • Repo access, architecture walkthrough, and a starter environment
  • Product decisions (API shape, and mobile scope if that work starts)
  • Code review
  • Apple and Google developer accounts only if the optional mobile workstream is started

What success looks like

At the end of the term, the students can demo:

  1. Developer Platform — run health plus a real user journey, and show a clear pass or a useful failure
  2. Follio API — a third-party demo client reading a permitted profile, and a rejected request for a private one

Optional: installable iOS and Android builds that open and share a Follio. Nice if it happens. Not required for the course to be a success.

Plus a short handoff: architecture notes, how to run each piece, and known gaps.

Academic note

This is production-adjacent work on a private commercial codebase. Students will learn real auth, API design, and test infrastructure — not a greenfield toy app. Mobile release is extra. Scope is sized so two students can finish the required work in one term without owning the entire Follio product.
